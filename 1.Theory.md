# Theory

## What is Git?

Git is a version control system that tracks changes to files, especially code, over time. You can think of it like Ctrl+S/Cmd+S on steroids. It lets developers save different versions of their work, collaborate with others, and easily undo or review changes.

## Why use Git?
How do you manage your files at the moment?

### Example 1
- my_assignment.py
- my_assignment_2.py
- my_assignment_3.py
- my_assignment_3.1.py
- my_assignment_4.py
- my_assignment_final.py
- my_assignment_final2.py
- my_assignment_final_final.py
- my_assignment_final_for_realsies.py

This can get really annoying and messy. What if you try using the same file over and over

### Example 2
- my_assignment.py

- crapitdoesntworkanymore.py
- my_assignment_new.py

It's easy to lose track of when changes were made, perhaps changes you want to undo. It can reach a point where you decide to start again because it'll probably be quicker to do that than to find the mistake you made a few versions ago.


## How does git work?
Git keeps track of all the changes to a repository through 'diff's. Any change you make will be recorded as a change. Even when removing content, the old content will still exist in the diff, there will just be a note that some of it got removed in a later commit. 

Basic gist:

| save version | tracked_file | git_diff_file |
|--------------|--------------|---------------|
| 0.           |              |               |
| 1.           | apple        | +apple        |
| 2.           | pineapple    | +apple <br> +pine   |
| 3.           | pine         | +apple <br> +pine <br> -apple |
etc.

This process works really well for plaintext files (e.g. code). It will struggle if you try to include large data files in your repo. 

## Workflow
Git forces you to work a very specific way. It is a way that is not very intuitive for most people, but a way that is very practical for record keeping. It follows a standard procedure that is used throughout most major software companies, aimed at keeping different working environments separate.

**Developer environment**: Where you (the developer) make changes to local code

**Staging environment**: Where you put code up for review, so edits and bugfixes can be made before making it public

**Production environment**: The public facing code. This should **ALWAYS** be functional.

In the context of git, the process looks like this:
1. *[dev]*   Save files normally 

    `Ctrl+S`

2. *[stage]* Add them to a staging area 

    `git add my_file`

3. *[stage]* Make sure that all the changes are good. If bugs found, fix and readd to staging area 

    *edit my_file and save*

    `git add my_file`

4. *[prod]*  Commit the changes. Leave a message about the change made. **THIS IS IRREVERSIBLE**

    `git commit -m "Added a function that solves the Riemann Hypothesis"`

Commits act like checkpoints in your code history. It is useful to combine related changes together in one commit. While it is not *literally* irreversible, it is really finicky to try to edit prior commits, and doing so defeats the purpose of using Git in the first place. If you find things that need to be changed in older commits, best practice is to leave them in the history, and just create a new commit with the necessary changes. 


## What is Github?
GitHub is an online platform where developers store, share, and collaborate on code. Think of it as cloud storage aimed specifically at Git users. It uses Git to track changes, making it easier for teams to work together, manage projects, and keep a history of their code.
