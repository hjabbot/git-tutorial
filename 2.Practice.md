## 1. Creating a Git Repository
As mentioned earlier you do not NEED Github in order to use Git, however I recommend that you do. Most of this tutorial will be done using the assumption that you are using Github.

### Local Git Only
1. Create a folder and get inside

    ```
    mkdir /path/to/project_name
    cd /path/to/project_name
    ```

2. Initialise git, do an ls to make sure it worked

    ```
    git init
    ls -la
    ```

    There should now be a directory called `.git` inside your project.

### Using Github
There are a couple ways to do this: you can either create a git repo locally (using instructions above), and then push it to a repo on under your Github account, or you could create a repo through Github, and pull it to your local computer. I find the latter to be the cleaner, easier-to-remember method of the two, so it is detailed below.

1. Log in to Github. Locate the green "New" button (either on `github.com` after logging in, or go to `Profile Icon->Repositories` and find it there). Click it.
2. Set up your repo name, and fill in the required fields. Create the repository.
3. From your new repo, click the green `<> Code` dropdown menu, and copy the SSH code 

    e.g. `git@github.com:hjabbot/git-tutorial.git`

4. In a terminal window, navigate to the directory you want your project in (the parent folder) and clone the repo. Then go inside that directory. 

    ```
    cd /path/to/parent
    git clone git@github.com:<username>/<reponame>.git
    cd <reponame>
    ls -la
    ```

    The `ls -la` should show a bunch of default files common to any git repo. 

If you did your setup properly from **0.Homework**, then everything should have gone without a hitch. Ask questions now if any of these steps failed, as this is the most likely time for issues to arise. 


## 2. Git Basics
Now that your repo is set up, you can write and track changes. Feel free to follow loosely and do this with your own files, or follow along and use the files provided in this tutorial's repo. 

The commands that we will learn first are:
- `git status`
- `git add`
- `git commit`

Run `git status` now. It should say something like
```
> git status

On branch main

No commits yet

nothing to commit (create/copy files and use "git add" to track)
```

`git status` will tell you what the current state of your local repo is. It will list out what files are being tracked, which tracked files have been modified since the last commit, and what branch you're working off of (more on that later). You will be typing this command a lot.

Let's create a file and start tracking it. I will make a new file `greetings.py` and add a message for the user in it.
```
print("Hello Wold!")
```
Save the file, and run `git status` again.
```
> git status

On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	greetings.py

nothing added to commit but untracked files present (use "git add" to track)
```

Now there is an untracked file that Git recognises. Untracked means that Git is not following the changes, any edits made to this file will not be saved. If you delete it, it will be gone forever. Let's change that.
```
> git add greetings.py
> git status

On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
	new file:   greetings.py
```

Now the file `greetings.py` has been added to the 'staging' area. The changes have not been saved yet, this is your final chance to make edits before commiting it to the repo permanently. Let's look inside the file. 

```
> cat greetings.py

print("Hello Wold!")
```

Oh no! There's a typo! Good thing we caught it before commiting the change, otherwise the wold would have laughed at us. Fix and save.

```
> cat greetings.py

print("Hello World!")
```
That's better. Run `git status` again.

```
> git status

On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
	new file:   greetings.py

Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   greetings.py
```

You may think that since you edited the file that's in the staging area, the changes will be saved to the staging area. This is not the case. Any changes made to files already in the staging area have to be readded, otherwise the old version of the file will be saved when you commit. 

```
> git add greetings.py
> git status

On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
	new file:   greetings.py
```

Now that we're happy with this new file, let's commit it to our repo. 
```
> git commit -m "Adding a friendly message to the user"
```
Our file is now being tracked by git. Running `git commit` adds all files in the staging area to the repo in a somewhat permanent manner. 

### Side note:

Sometimes you accidentally add a file to the staging area. If you do this, you can run `git restore --staged <filename>` to remove it from the staging area. 

## 3. Interacting with Github

Pushing and pulling are how you synchronise your local repo to the version on Github. Pushing is uploading your local changes to the cloud. Pulling is downloading remote changes to your local machine. A pull is comprised of two steps; fetching and merging. Fetching downloads remote metadata, basically telling you if there are changes to be pulled or not. Merging actually combines your local code with the remote version you just pulled. 

The basic commands are
- `git push`
- `git fetch`
- `git merge`
- `git pull`

The last thing we did was save the repo locally, but Github still has no idea about the changes we made. Let's synchronise the remote version of the repo.

```
> git push
```
If you go to your repo in your browser and refresh the page, you should see your new file pop up, along with some metadata (e.g. how long ago the push was). 

### Side note:
*One of the most dangerous commands in git is `git push --force`. This command has the power to rewrite your git log, which can cause major headaches and permanent data loss if used incorrectly. You have been warned.*

For this example, we are working on our own repos, so we don't expect there to be any reason to pull new changes in from Github. If, however, we were collaborating on a project with someone else, it would be prudent to regularly run a `git pull` to make sure our codebases are not diverging too much. If left unchecked, this can cause conflicts later down the line which can be messy to untangle. 

`git pull` is exactly equivalent to running `git fetch` and `git merge` back to back. You will rarely need to do these commands separately, and `git pull` is realistically all you need for this tutorial. Go ahead and run it now

```
> git pull

Already up to date.
```
No changes should have been made to the Github version of your code, so it doesn't need to do anything. 

It is good practice to keep your local version of the repo up to date with the Github version, particularly if working collaboratively. In order to pull the changes in, run the following command:

```
> git pull origin main

Already up to date.
```

Here, `origin` is shorthand for the Github URL of your repo, and `main` is the branch being pulled (more about branches later). If you were already in `main`, this `git pull origin main` is exactly equivalent to `git pull`.

## 4. Record keeping
### History
Git keeps track of each committed change in the repository. In order to see the history through the terminal, run the `git log` command

```
> git log

...

commit 6d2fc54647a30da7ef8b3962b0be68c9255df49f
Author: hjabbot <42661345+hjabbot@users.noreply.github.com>
Date:   Fri Sep 18 21:44:58 2026 -0600

    Initial commit
```

The long garbled string in the first line (6d2...49f) is called the commit *hash*. It is a unique identifier that is specific to that one exact change. We will be using this later. The way it is formulated is a one-way function, and each subsequent commit will depend on the previous hash. This is the reason that changing commits in the past is annoyingly difficult.

By default, `git log` will output to a `less` terminal file reader. To exit, simply press 'q'.

`git log` spits out quite a few lines, sometimes all we need is the hash. To see a condensed version, add the "--oneline" flag to the command

```
git log --oneline

...
6d2fc54 Initial commit
```

Notice that the hash is much shorter this time. Why? Well the hash in this version is actually just the first 7 bytes of the original 40-byte hash. The whole 40-byte hash is a UID that should remain unique even across the entirety of Github. When you are modifying a repo, it's assumed that you're only referencing the commits in that specific repo, so a shorter UID that is only unique within your repo is all that is needed. 

TL:DR; the shorter 7-byte hash is all we'll need in the upcoming section.

### Diffs

`git status` so far has been useful in telling us that there are changes that are or aren't being tracked within our repo, however it doesn't tell us what those changes actually are. The two most useful things to see would be
1. The difference between the current state and the staged state of the repo
2. The difference between the staged state and the committed state of the repo

Go ahead and make a change to one of your tracked files and save it.

```
> git status

On branch main
Your branch is up to date with 'origin/main'.

Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   greetings.py

no changes added to commit (use "git add" and/or "git commit -a")
```
There is a change in our dev environment, but not in our staging or production environments. To see the difference, run `git diff`

```
> git diff

diff --git a/greetings.py b/greetings.py
index 1dc45ac..15272a9 100644
--- a/greetings.py
+++ b/greetings.py
@@ -1 +1,2 @@
-print("Hello World!")
\ No newline at end of file
+print("Hello World!")
+print("This is a change")
```

Now add the file to the staging area and check the output of git diff.
```
> git add greetings.py
> git diff
```
This should output nothing. That is because once the file has been added to the staging area, there is no difference between the dev environment and the staging environment. If instead we run `git diff --staged`:

```
> git diff --staged

diff --git a/greetings.py b/greetings.py
index 1dc45ac..15272a9 100644
--- a/greetings.py
+++ b/greetings.py
@@ -1 +1,2 @@
-print("Hello World!")
\ No newline at end of file
+print("Hello World!")
+print("This is a change")
```
We get out the same diff as we had before we added the file to staging. That is because the difference is now between the staging and the production environment.

Let's remove the change from the staging area without committing. 
```
> git restore --staged greetings.py
```
The repo should now be in the same state as it was at the last commit.


## 5. Undoing changes
There are 3 levels of undo within git. 
- `git restore`
- `git reset`
- `git revert`

We have already seen `git restore`. This is the softest level of undo. It is used to undo changes to a single file that have not yet been committed. 

Make some disposable changes to a file that has previously been committed to the repo. Then let's run `git restore` on it

```
> git status

On branch main
Your branch is up to date with 'origin/main'.

Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   greetings.py

> git restore greetings.py
> git status

On branch main
Your branch is up to date with 'origin/main'.
```

The changes you made should now be gone from the file.

`git reset` works very similarly, however it is not used for a single file, but rather updates every modified file. It requires an argument that is the state that you want to reset your repo to. This is where those hashes from earlier come in handy.

Use `git log --oneline` to find an earlier commit that you're happy to reset your repo to. Copy the hash from that commit. Then run
```
> git reset <hash>

Unstaged changes after reset:
M	greetings.py
```

Your committed history should now be limited to the point up to that commit you just reverted to. This command does not remove the changes made since then. Run a `git diff` and you should see all the changes that you made to your file since that commit, even if it was multiple commits ago. 

It can be annoying to have to search for the hash of the specific commit you want, especially if you remember how many commits ago it was. For this reason, there is a shorthand hash `HEAD`. `HEAD` is an alias for the most recent commit. `HEAD~1` is shorthand for the previous commit. In general, `HEAD~N` is shorthand for N commits ago.

Usage:
- `git reset HEAD` brings changes out of your staging area and back into your dev environment
- `git reset HEAD~1` brings changed out of your staging area, and your most recent commit and back to your dev environment. Your git history will be reset to the PREVIOUS commit.
- `git reset HEAD~2` goes back 2 commits, etc. etc.

- `git reset --hard HEAD` This is a destructive command. This will reset your repo to the state it was in at the last commit **and discard any recent uncommitted changes**. 
- `git reset --hard HEAD~1` will reset your repo to one commit ago **and discard your most recent commit**.

`git reset --hard` is a powerful command, however if you had pushed changes to Github before doing the reset, then you may be confused the next time you try `git pull`. Since doing a `reset` essentially puts your git repo into a state it was in the past, trying to synchronise your local copy with the remote copy will result in the more recent commit (the one you tried undoing with `reset --hard`) being pulled into your local version again. 

In order to get your Github version to 'go back in time' to a previous commit, the best command is `git revert`. This command will not erase history, but rather determine the exact inverse of the offending commit and apply a new commit to undo it.

Try do the following:
```
> git log --oneline
> git revert HEAD
> git log --oneline
```
When `git revert` is run, a text editor will pop up prompting you to create a new commit message. Default message is "Revert '\<OLD COMMIT MESSAGE>'", which is usually fine. Save this, and then when you look at the log again, you should see a new commit that is "undoing" the `HEAD` commit. 

You can revert any specific commit while preserving commits that are newer than it, since we're just undoing one specific commit by making a new commit that does the opposite of the one you want to remove. Just be careful, editing files like this is very prone to errors and conflicts. e.g. if you're trying to undo a commit but the changed lines have been changed since that commit you're trying to revert, things get confusing and conflicts can occur.

e.g.
```
Auto-merging blah.txt
CONFLICT (content): Merge conflict in blah.txt
error: could not revert e018dab... 2
hint: After resolving the conflicts, mark them with
hint: "git add/rm <pathspec>", then run
hint: "git revert --continue".
hint: You can instead skip this commit with "git revert --skip".
hint: To abort and get back to the state before "git revert",
hint: run "git revert --abort".
hint: Disable this message with "git config set advice.mergeConflict false"
```


## 6. Branches
Perhaps one of the most useful features of Git is the ability to create branches. Branches act like "alternate universes" where you can test changes to code without affecting your known existing functional codebase. It's very useful when developing new features, fixing heavily embedded bugs, refactoring old code, or working collaboratively. 

The basic idea is that you have a stable working source, usually called "main". You then branch off of that, develop some code in isolation, and then when you're happy with it, you can merge it back into the "main" code. 

The history of both get merged chronologically, and so long as no conflicting edits have happened on main, the code can be merged safely and cleanly. This way, anyone else looking at the code (including yourself at a different time in the future) can always access a working version of the codebase. 

### Creating branches

![Alt Text](https://cpske.github.io/ISP/git/git-branches.png)

The first branch in any repo is called `main` (or `master` if you're using an old version of git). There is nothing special about this branch, but it is the default naming convention. To create a new branch:

```
> git status
On branch main
...

> git branch my_new_branch
> git checkout my_new_branch
Switched to a new branch 'my_new_branch'

> git status
On branch my_new_branch
...

```

From this point on, any changes you commit will be added to this new branch. 

`git branch` creates a new branch

`git checkout` is the command you use to change between branches.

### Side note:
One shortcut you can use is to create a new branch and swap to it in one command:
`git checkout -b my_new_branch`


### Merging

Once you're happy with your changes, you can fold them into the `main` branch of your repo with the `git merge` command. To do this, 
```
# Merges feature_branch into main
> git checkout main
> git merge feature_branch
```

Sometimes your feature branch will take a long time to develop. There may be some changes happening to `main` while you work on your feature branch. To make sure that they always stay compatible, it is a good idea to periodically pull changes from `main` into your feature branch. 

```
# Merges main into feature_branch
> git checkout feature_branch
> git merge main
```

Note that in doing these, the `merge` does not destroy the branch, it just combines the two. Both `main` and `feature_branch` will continue to exist after either of these commands.

If you are working with Github, then it would be better practice to merge with the most up to date branch from Github instead of your local version of `main`. This is particularly true if you are collaborating with others. There may be changes to `main` that you have not pulled in yet. When in doubt, always treat the Github version of your code to be the official version, and not your local version.

These two scenarios then become
```
# Merges feature_branch into main
> git checkout main
> git pull origin main
> git merge feature_branch
```

```
# Merges main into feature_branch
> git checkout feature_branch
> git pull origin main
```

### Merge conflicts

If one line is changed in both branches before being merged, then a "merge conflict" will occur. In this case, it is not safe for git to assume which branch takes priority, and so it will spit out an error asking for user intervention before proceeding. To see this cleanly, let's create a new file and edit it across two branches.

```
# Create a new file with some text, add it to git
> git checkout main
> `echo "Schroedinger's cat is ..." > physics_conundrum.txt`
> git add physics_conundrum.txt
> git commit -m "Proposing unsolved problem"

# Create a new branch, edit the line and commit
> git checkout -b solving_quantum_mechanics
> echo "Schroedinger's cat is dead" > physics_conundrum.txt
> git add physics_conundrum.txt
> git commit -m "Solving unsolved problem"

# Go back to main, edit the same line, and commit
> git checkout main
> echo "Schroedinger's cat is alive" > physics_conundrum.txt
> git add physics_conundrum.txt
> git commit -m "Solving unsolved problem in a different way"

# Try merging only to recieve an error
> git merge solving_quantum_mechanics

Auto-merging physics_conundrum.txt
CONFLICT (content): Merge conflict in physics_conundrum.txt
Automatic merge failed; fix conflicts and then commit the result.

> git status

On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   physics_conundrum.txt

no changes added to commit (use "git add" and/or "git commit -a")


# Have a look at the conflicting file
> cat physics_conundrum.txt

<<<<<<< HEAD
Schroedinger's cat is alive
=======
Schroedinger's cat is dead
>>>>>>> solving_qm

```

Here, we edited the same line, so a merge conflict occured. After this, you will notice that the file being editted `physics_conundrum.txt` had a bunch of new lines that git added (the `<<<<, =====, >>>>` lines). To solve the merge conflict, edit the file to have the absolute version that you want to commit. Then run a `git status` to make sure it's correctly solved, and finally run a `git commit`

```
# Replace the conflicting file with the definitive version
> echo "Schroedinger's cat is alive" > physics_conundrum.txt
> git add physics_conundrum.txt

# Make sure that the conflicts have been fixed
> git status

On branch main
All conflicts fixed but you are still merging.
  (use "git commit" to conclude merge)

# Commit the definitive version
> git commit
[main e295b70] Merge branch 'solving_quantum_mechanics'
```


### Stash
Sometimes while working on a branch, you want to swap between branches, perhaps to work on something else. Maybe you want realise that the code you're writing is better suited for another branch instead. In cases like these, we don't want to commit our changes to our current branch, but rather stash them away somewhere else to be retrieved later. That is where `git stash` comes in. Think of the `stash` as a temporary holding area. It's not very organised, but it contains whatever you put into it in the order you put it in. 

Let's say that you're in `main`, making some changes, but then realise it would be better to be working in a feature-branch instead. 

```
> git checkout main
> echo "Assume cow is spherical" >> physics_conundrum.txt
> git checkout solving_quantum_mechanics

error: Your local changes to the following files would be overwritten by checkout:
	physics_conundrum.txt
Please commit your changes or stash them before you switch branches.
Aborting

> git stash

Saved working directory and index state WIP on main: e295b70 Merge branch 'solving_quantum_mechanics'

> git checkout solving_quantum_mechanics
> git merge main    # not necessary but good practice
> git stash pop     # Adds most recent stash item to changes in the current branch
```

There are many `git stash` commands, `pop` has generally been most useful to me. The stash needs to be manually managed, and so best practice is to keep it short. You can add items to your stash indefinitely, however you will lose track of what changes become what items in the stash list. It is a last-in-first-out ordered list, meaning that every time you add something to the list, it becomes the 0th item, and everything else gets shuffled back one. 

```
stash@{0}   # Most recent item added to the list
stash@{1}   # Previous most recent item added to the list
...
stash@{n}   # nth last item added to the list
...
```

When you `pop` the stack, you are simultaneously reading in the most recent item (`stash@{0}`) and removing it from the list. That means that the nth item now becomes the (n-1)th item. Since they're not labelled, you can see how having a long list of items that change index when you modify the list can become difficult to manage. Hence why I would recommend only ever having 1 or 2 items in your stash.
